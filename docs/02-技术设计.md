# 技术设计

## 1. 总体架构

采用浏览器界面＋本地 Python 服务。浏览器展示与轮询任务状态；Python 管理查表、精确搜索、构造、验证和缓存。

- 前端暂定 HTML、CSS、原生 JavaScript，静态资源随项目提供，不依赖外部 CDN。
- 本地服务优先使用 Python 标准库；开发实施前再确定是否确有必要引入框架。
- 服务只绑定 `127.0.0.1`，检查请求来源与 Host，使用启动时生成的本地会话标识保护任务接口。
- 计算在独立工作进程中进行，使浏览器与服务保持响应，并支持真正取消计算。
- 本地服务适合个人使用，不作为公开网站服务部署。

建议开发目录如下，**本阶段不创建这些代码文件**：

```text
app/             本地服务、任务管理、统一结果协议
engine/          判定、搜索、多方案、长整数构造、验证
web/             输入与结果页面
vendor/ss/       固定版本的上游代码和许可
data/            上游数据、规则元数据、补充见证与索引
tests/           规则、算法、接口及页面测试
tools/           数据审查、构建索引、性能测量
docs/            本阶段工程文档
```

## 2. 统一问题模型

输入保存为数字串 `s`，在等号处切成非空连续段。每段由连续数词、二元运算符和括号组成，数字顺序保持不变。

使用 `fractions.Fraction` 保存精确值。默认规则与严格规则分别求值，不混用不同规则下的结论。

结果必须分别包含：存在性（是／否／未知）、依据、搜索状态、已验证方案。数学存在性与计算任务的完成状态不能合并成一个布尔值。

## 3. 判定与生成流程

1. 校验输入及规则；单个数字直接处理。
2. 查询适用规则的已核验数据；有现成见证则先验证并展示。
3. 对至少 16 位的输入，优先执行归零构造，迅速提供第一条单等号方案。
4. 其余输入启动精确表达式搜索，优先从中间尝试单等号切分。
5. 若用户允许多个等号，则在需要时增加切分段数。
6. 每找到一条方案，独立验证、去重、排序并逐步返回。
7. 达到目标数量、搜索完成、资源上限或用户取消时结束当前任务，并返回准确状态。

对于大于 `9989858` 的整数，可依据项目定理提前告知一个等号的方案存在；具体规则的适用性必须在实施阶段审查，不能把文档中的规则等价说明当作未经检查的运行结论。

### 数据表的使用边界

上游的 19515 条单等号反例表只覆盖 2–7 位，且需要核验完整性与规则适用性。单个数字另行处理，不能因为没有出现在表中就判为可解。

默认规则的多等号分类表可提供 1317 个见证。严格规则下，必须验证见证语法；见证含前导负号时不能直接沿用“有解”结论，应重新搜索或使用重新生成的严格分类表。

默认规则下“完全无解”的条目，在严格规则表达式集合确为其子集时仍然无解；此包含关系也要有明确的实现约束。

上游报告有 412 个弱串需要前导负号，该数字用于审查基准，不代替逐条规则核验。

## 4. 精确搜索与多方案

沿用上游按子串递归计算值集的思路：整段拼接是一种值；对每个根切分点，将左右子串值集用四种运算组合，跳过零分母。

为了给出多条方案，不能直接使用上游“每个值只保留第一条表达式”的策略。增加 `值 → 有限个表达式结构` 的记录，保留不同运算结构和切分方式的候选。

- 表达式采用语法树保存，再按优先级输出括号。
- 对每个值保留的见证数量有上限，以控制内存。
- 若需要精确无解判定，必须完整保存可达值集；见证截断和可达值截断是不同事情。
- 若为了快速搜索截断了可达值集，该搜索结果只能证明找到的方案，不能证明无解。
- 两段值集求交集；多段搜索对当前公共值集合为空的分支剪枝。
- 见证生成使用规则明确的严格／默认版本，不能让通用解析器接受的任意负号进入搜索结果。
- 第一批结果与后续补充结果分开，避免为了凑足 5 个而延迟展示第一条。

方案以规范化语法树去重：忽略空格和冗余括号；减法、除法保留结合关系。不交换左右操作数，以免改变数字顺序。

排名优先级暂定：等号数量、运算符数量、括号深度、显示长度。该排名只在已找到的方案中比较。

## 5. 长整数的构造路径

长整数不能一律计算整段的所有可能值。为至少 16 位的数字串使用以下结构性方法：

1. 选择一个切分，使左右两段各至少 8 位。
2. 每侧取一个 8 位连续窗口。依据项目归零结论，该窗口中应存在可归零的素子串。
3. 用已核验的素可归零串索引找到子串，并取其严格规则归零表达式 `Z`。
4. 将该子串之前与之后的数字按原顺序用乘法连接，构成值为零的整侧表达式。
5. 左右两侧用一个等号连接，得到 `0=0` 的见证，并验证。

例如某侧为 `p + 子串 + q`（这里 `+` 表示数字串拼接），可构造 `P*(Z)*Q`。当 `p` 或 `q` 为空时省略相应因子；这里的 `P`、`Q` 只能由原有数字组成。

若剩余数字有先导零，则切成合法数词或单个数字，不能删除零。所有归零表达式都必须通过严格语法验证，确保无需前导负号即可使用。

补充资源：为上游 6534 条素可归零串生成并独立验证归零见证，保存为本项目派生数据。上游列表本身不保证已经携带这些见证；构建成本与覆盖性必须实测。单个 `0` 作为明确的归零基础情况处理，不直接依赖上游仅枚举切分的函数。

通过调整切分点、选择不同窗口或不同归零子串，可提供多种长整数方案。不得保证每个输入都能产生用户请求的全部数量。

**8–15 位输入不能普遍套用两侧各 8 位的构造。** 这一区间仍需查表与搜索，是主要性能风险。约 8200 万候选的完整筛选仅用于离线验证或重建数据，不在每次网页输入时运行。

## 6. 独立验证

验证器与搜索器使用不同的求值实现。每个公开方案必须通过以下检查：

- 恰好保留原数字串的全部数字及顺序。
- 只包含允许的字符、数词和运算语法。
- 当前规则允许其负号位置；当前等号设置允许其段数。
- 每个等号段非空；数词无非法先导零；分母不为零。
- 各段用精确分数独立求值，且全部相等。

通用 `eval()` 不用于计算用户输入或见证。显示共同值时也保留精确分数，近似小数只能作为附加展示。

## 7. 数据与可信边界

取得数据时固定上游提交版本，保留原文件、许可及版本记录。检查 manifest、文件散列、排序、计数、集合关系和见证；散列一致只说明文件一致，不证明数学结论正确。

运行上游单元测试与默认验证，再对关键边界独立复算。`--deep` 对发布条目的复核不能单独证明遗漏的候选不存在；完整性需要审查筛选逻辑，并按需要重新运行筛选。

本应用“依据项目定理”的结论应保留来源。第一版不宣称提供了形式化证明或独立重新完成了全部约 8200 万候选的计算证明。

## 8. 接口草案

接口通过字符串传递整数和有理数，不使用浮点数表示数学值。

| 接口 | 用途 |
|---|---|
| `POST /api/jobs` | 提交数字串、规则、等号设置、目标数量 |
| `GET /api/jobs/{id}` | 读取判定、搜索状态、已验证方案、限制原因 |
| `POST /api/jobs/{id}/cancel` | 取消任务，保留已验证方案 |
| `GET /api/info` | 读取应用版本、上游数据版本、功能与输入上限 |

任务结果字段草案：`existence`、`basis`、`search_state`、`solutions`、`limits`。

单条方案字段草案：`expression`、`segments`、`common_value`、`equals_count`、`verified`。

搜索状态：运行中、已达到目标、已穷举完成、已取消、达到资源上限、执行错误。达到目标方案数量不等于完成全部穷举。

## 9. 资源管理

初始软搜索时限暂定 10 秒；达到时限时显示当前结果，并允许继续搜索。具体值在性能测量后调整。实现还需要有限缓存、单任务预算、进程终止与缓存清理，避免一次复杂输入占满内存。

基准数据覆盖短串、7 位边界、8–15 位困难候选、16 位构造及 64／256 位输入。最终依据测量确定支持范围与交互时限，不用定理存在性代替性能保证。
